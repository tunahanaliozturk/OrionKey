# OrionKey 0.5.0 — Analyzer, Code-Fix, and Stabilization (Phase D)

**Date:** 2026-05-23
**Status:** Approved
**Release:** 0.5.0 (fourth slice of the 0.2.x → 0.5.x roadmap; the last release before 1.0)

## Context

OrionKey already reports five diagnostics: `ORIONKEY001` (not a readonly partial struct),
`ORIONKEY002` (unsupported value/strategy type), `ORIONKEY003` (string value requires an
explicit strategy), `ORIONKEY004` (incompatible strategy/value pairing), `ORIONKEY005`
(member collision with generated output). Phase B may add `ORIONKEY009`–`ORIONKEY010`
for integration-emitter edge cases. None of these have code-fix providers; users see the
diagnostic and edit by hand.

Phase D is the last release before 1.0. It adds new diagnostics that catch real misuse,
adds code-fix providers for the diagnostics where a mechanical fix exists, runs a
performance pass on the source generator's incremental pipeline, and shakes out any
remaining 0.x edge cases so 1.0 can be a bug-fix-only release going forward.

## Goals

1. Add three new diagnostics: `ORIONKEY006`, `ORIONKEY007`, `ORIONKEY008`.
2. Add code-fix providers for `ORIONKEY003` and `ORIONKEY005`.
3. Source-generator performance pass: verify the incremental pipeline caches per-type
   work correctly; add a benchmark project that measures compile-time impact on a
   synthetic large solution.
4. API-stability sweep: verify nothing in the public surface should change before 1.0.

## Non-goals

- No new ID strategies (Phase A).
- No new integration emitters (Phase B).
- No AOT/trimming changes (Phase C).
- No breaking changes — 0.5 is the last 0.x; 1.0 follows shortly after with the same
  public API.

## New diagnostics

| ID | Severity | Trigger | Message |
|---|---|---|---|
| `ORIONKEY006` | Warning | An EF Core entity uses an OrionKey ID as its key but the project does not reference `Microsoft.EntityFrameworkCore` (so the generator did not emit a `ValueConverter`) | `'{0}.{1}' is a strongly-typed id used as an EF Core key; reference Microsoft.EntityFrameworkCore so OrionKey can generate the value converter, or supply one explicitly.` |
| `ORIONKEY007` | Info | `[OrionId]` struct declared but never referenced anywhere in the compilation | `Strongly-typed id '{0}' is declared but never used; remove the declaration or reference it from a model.` |
| `ORIONKEY008` | Suggestion | Property named `Id` or `*Id` of type `Guid` / `long` / `int` / `string` on a class that looks like an entity, and an OrionKey ID type already exists for that primitive | `Property '{0}.{1}' uses a bare {2}; consider replacing it with the strongly-typed '{3}'.` |

`ORIONKEY006` runs in the source generator (it already inspects the compilation for the
EF Core reference). `ORIONKEY007` and `ORIONKEY008` are best implemented as separate
analyzers (`DiagnosticAnalyzer`) because they require cross-compilation symbol queries
that the source generator does not need to perform during its normal pipeline.

## Code-fix providers

| Provider | Diagnostic | Fix |
|---|---|---|
| `StringStrategyCodeFixProvider` | `ORIONKEY003` | Offers five quick-fixes: replace `[OrionId<string>]` with `[OrionId<string, Ulid>]` / `[OrionId<string, NanoId>]` / `[OrionId<string, Cuid2>]` / `[OrionId<string, Ksuid>]` / `[OrionId<string, ObjectId>]`. Cursor lands on the strategy so users can swap easily. |
| `MemberCollisionCodeFixProvider` | `ORIONKEY005` | Single quick-fix: remove the user-declared member that collides with the generator's output. Preserves attributes and comments where possible; falls back to a "remove the entire member" action. |

Both code fixes are registered under a new `Moongazing.OrionKey.CodeFixes` project
(netstandard2.0, references `Microsoft.CodeAnalysis.CSharp.Workspaces`). The project
is packed into the same NuGet package as the generator, in `analyzers/dotnet/cs`, so it
is picked up automatically by Roslyn-aware IDEs.

## Performance pass

- Add `bench/Moongazing.OrionKey.GeneratorBenchmarks` that runs the generator over a
  synthetic compilation with N declared `[OrionId]` structs (N = 1, 10, 100, 1000) and
  measures the per-generator-pass cost.
- Verify the incremental pipeline does *not* regenerate companions for unchanged
  declarations by introducing a single-character edit to one of the N structs and
  asserting only that struct's output is recomputed.
- Cache `OrionIdParser.TryParse` results per `INamedTypeSymbol` if the benchmark
  reveals work being repeated unnecessarily; otherwise leave the pipeline alone.

## API-stability sweep

This is a desk exercise, not a code change in most cases.

- Walk every `public` type/member in `Moongazing.OrionKey` and `Moongazing.OrionKey.Testing`
  and decide: stable for 1.0, hide it (move to `internal`), or rename it.
- Confirm that the eight strategy marker structs, the `OrionId` attributes, the
  `OrionKey` facade, `OrionKeyOptions`, `OrionKeyDiagnostics`, `OrionGuidComparer`,
  and the testing scope are the locked surface.
- Anything not on that list either becomes `internal` or gets a brief justification in
  the changelog for why it stays `public`.

## Error handling

The new analyzers and code-fix providers must never throw on malformed input; they
should report no diagnostic / offer no fix when the AST is incomplete (typical mid-typing
state in an IDE). Tests cover the obvious mid-edit cases.

## Testing

- Diagnostic tests for each new ID (`ORIONKEY006`–`ORIONKEY008`).
- Code-fix tests using the standard Roslyn testing harness; assert the fixed text equals
  an expected fixture per case.
- Performance benchmark numbers captured into `docs/generator-benchmarks.md` so future
  PRs can compare against a baseline.
- Existing 122+ tests continue to pass.

## Rollout

Single release `0.5.0`, the last 0.x. The new diagnostics may surface in consumer code
that previously compiled clean; they default to Info/Warning/Suggestion (not Error), and
`ORIONKEY007`/`008` can be tuned per project via `.editorconfig`. After 0.5.0 ships and
soaks for a release cycle, **1.0.0** follows as a bug-fix-only release that marks the
public API stable.
