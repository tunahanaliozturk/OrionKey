# OrionKey 0.4.0 — Native AOT & Trimming (Phase C)

**Date:** 2026-05-23
**Status:** Approved
**Release:** 0.4.0 (third slice of the 0.2.x → 0.5.x roadmap)

## Context

OrionKey targets `net8.0;net9.0;net10.0` and is consumed as a NuGet package whose
source-generated code lands inside the consumer's compilation. Generated converters and
factories are static (no reflection at the call sites we control), but the surrounding
discovery paths — `TypeDescriptor.GetConverter`, EF Core convention scanning, ASP.NET
Core model binding — use reflection. Those paths are already AOT-friendly when invoked
on types reachable from roots, but they only stay friendly if the project metadata says
so and the right annotations are in place.

Phase C makes OrionKey's promise to AOT and trimming users explicit and verified: every
runtime project is marked `<IsAotCompatible>true</IsAotCompatible>`, every reflection
use is justified by an annotation or removed, and a real `PublishAot=true` sample app
exercises the full surface in CI.

## Goals

1. Mark every runtime project AOT-compatible and resolve every warning the toolchain
   raises at build time and during `PublishAot`/`PublishTrimmed`.
2. Add a `sample/Moongazing.OrionKey.AotSample` that publishes with `PublishAot=true`,
   exercises every ID strategy plus every Phase B integration emitter currently active,
   and runs successfully as a native binary.
3. Wire an AOT-publish step into CI so regressions surface before they ship.
4. Document the AOT/trimming story in README and per-package READMEs.

## Non-goals

- No new ID strategies (Phase A).
- No new integration emitters (Phase B).
- No new analyzer / code-fix work (Phase D).
- No new public API surface — Phase C is purely metadata, annotations, and verification.
- No support for `PublishSingleFile` beyond what AOT-clean already implies.

## Reflection audit

The audit is the heart of Phase C. We catalogue every place reflection occurs and
classify it as Safe (no annotation needed), Annotated (add `[DynamicallyAccessedMembers]`
or `[DynamicDependency]`), or Removed (rewrite to a static path).

| Location | Classification | Action |
|---|---|---|
| Generated `TypeConverter` discovery via `[TypeConverter(typeof(<Name>TypeConverter))]` attribute | Safe — attribute is statically discoverable by the trimmer | None |
| `TypeDescriptor.GetConverter(typeof(TId))` (consumer-side, in ASP.NET model binding) | Annotated — emit `[DynamicDependency(DynamicallyAccessedMemberTypes.All, typeof(<Name>TypeConverter))]` on the generated TypeConverter class | Update `TypeConverterEmitter` |
| EF Core convention discovery of `[ValueConverter]`-derived classes | Safe — EF Core 8+ has its own trim annotations; our generated converter is reachable through the entity model | None |
| `System.Text.Json` `[JsonConverter]` attribute on the generated converter class | Safe | None |
| `Trace.TraceWarning` in `OrionKeyDiagnostics` | Safe — `Trace` is AOT-compatible | None |
| `Meter`/`Counter` in `OrionKeyDiagnostics` | Safe — `System.Diagnostics.Metrics` is AOT-compatible | None |
| Source-generator code itself (runs at compile time only) | N/A — never runs in the published app | None |
| Phase B integration emitters (Dapper, Newtonsoft, MongoDB, Swashbuckle) | Library-dependent — each will be audited; some libraries are not yet AOT-compatible | Document per-emitter status |

If a Phase B integration library is not AOT-clean (Swashbuckle in particular has known
trim warnings as of 2026), the OrionKey emitter still ships, but the AOT sample only
exercises emitters whose target library is AOT-clean. The remaining ones gain an
`OrionKey.AotIncompatible` doc note rather than being silently broken.

## Sample app

```
sample/Moongazing.OrionKey.AotSample/
├── Moongazing.OrionKey.AotSample.csproj   (<PublishAot>true</PublishAot>)
├── Program.cs                              (top-level, exercises every strategy)
└── Ids.cs                                  ([OrionId] declarations for the sample)
```

`Program.cs` runs through this checklist and exits non-zero on any failure:

1. Generate one ID per strategy via `.New()`.
2. Round-trip each ID through `System.Text.Json`.
3. Round-trip each ID through `Parse`/`TryParse`.
4. For each Phase B integration whose library is AOT-clean: round-trip one ID through
   that library (e.g. Dapper to in-memory SQLite, MongoDB serializer to BSON byte array).
5. Print a one-line summary and exit 0.

## CI

`.github/workflows/ci-cd.yml` gains an `aot-publish` job:

```yaml
aot-publish:
  runs-on: ${{ matrix.os }}
  strategy:
    matrix:
      os: [ubuntu-latest, windows-latest]
  steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-dotnet@v4
      with: { dotnet-version: '10.x' }
    - run: dotnet publish sample/Moongazing.OrionKey.AotSample -c Release -r ${{ matrix.rid }}
    - run: ./sample/.../publish/OrionKey.AotSample
```

The publish step must complete with zero IL2026 / IL2104 / IL3050 / IL3053 warnings;
the run step must exit 0.

## Error handling

This phase introduces no new runtime error paths. The only failure surface is build /
publish time: a warning becomes an error under `TreatWarningsAsErrors`, which prevents
shipping a regression.

## Testing

- The existing test suite stays green throughout (122 tests + Phase B additions).
- New `TrimWarningTests` builds a synthetic consumer project with `<IsTrimmable>true</IsTrimmable>`,
  invokes the .NET SDK in-process, and asserts zero trim/AOT warnings — this catches
  regressions in PRs before the AOT job catches them in CI.
- The AOT sample is itself the most thorough end-to-end test.
