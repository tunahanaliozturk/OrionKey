# OrionKey 0.3.0 — Integration Emitters (Phase B)

**Date:** 2026-05-23
**Status:** Approved
**Release:** 0.3.0 (second slice of the 0.2.x → 0.5.x roadmap)

## Context

OrionKey 0.2 generates equality, comparison, parsing, `System.Text.Json`, BCL
`TypeConverter`, and EF Core `ValueConverter` companions for every `[OrionId]`-decorated
struct. The EF Core converter is conditional: the generator only emits it when the
consumer's compilation references `Microsoft.EntityFrameworkCore`. That same conditional
pattern extends naturally to four more widely-used integrations.

## Goals

1. Add four new conditional integration emitters: **Dapper**, **Newtonsoft.Json**,
   **MongoDB driver**, **Swashbuckle/OpenAPI**.
2. Ship a low-friction registration story so users do not hand-wire every generated
   type.
3. Preserve the zero-config experience for libraries that auto-discover converters
   (`System.Text.Json`, EF Core, ASP.NET Core model binding) — the new emitters are
   additive, not a replacement.

## Non-goals

- No new ID strategies (Phase A delivered those).
- No AOT/trimming work (deferred to Phase C).
- No analyzer or code-fix additions (deferred to Phase D).
- No replacement of any existing emitter.
- No support for libraries with no clear conditional-reference signal.

## New emitters

Each emitter follows the existing `EfCoreConverterEmitter` pattern: a probe in
`OrionIdGenerator.Initialize` checks `compilation.GetTypeByMetadataName(...)` for an
anchor type from the target package; if found, the emitter runs and adds a generated
file alongside the existing companions.

| Emitter | Anchor type (compilation probe) | Generated file | Generated type |
|---|---|---|---|
| Dapper | `Dapper.SqlMapper+TypeHandler\`1` | `<Id>.OrionId.Dapper.g.cs` | `<Id>DapperTypeHandler : SqlMapper.TypeHandler<<Id>>` |
| Newtonsoft.Json | `Newtonsoft.Json.JsonConverter` | `<Id>.OrionId.NewtonsoftJson.g.cs` | `<Id>NewtonsoftJsonConverter : JsonConverter<<Id>>` |
| MongoDB | `MongoDB.Bson.Serialization.IBsonSerializer` | `<Id>.OrionId.Mongo.g.cs` | `<Id>BsonSerializer : SerializerBase<<Id>>` |
| Swashbuckle | `Swashbuckle.AspNetCore.SwaggerGen.ISchemaFilter` | `<Id>.OrionId.OpenApi.g.cs` | `<Id>SchemaFilter : ISchemaFilter` |

### Per-emitter contract

- **Dapper** — `Parse(object value)` maps the underlying primitive to the ID; `SetValue`
  unwraps the ID's `Value`. For `Guid` IDs we set the `DbType` to `Guid`; for `string`
  IDs to `String` with size hints; for `long` to `Int64`.
- **Newtonsoft.Json** — symmetric to the existing `System.Text.Json` converter: read the
  underlying primitive token, construct the ID; write `Value` as the underlying token.
- **MongoDB** — `SerializerBase<TId>` overriding `Serialize`/`Deserialize` to round-trip
  through the underlying BSON primitive (`BsonString`, `BsonBinaryData` for `Guid`,
  `BsonInt64` for `long`).
- **Swashbuckle** — `ISchemaFilter.Apply` rewrites the schema for the ID type to the
  schema of its underlying primitive (e.g. `type: string`, `format: uuid` for `Guid`).

## Registration story

`System.Text.Json`, EF Core, and ASP.NET Core auto-discover converters via attributes /
conventions, so users currently write zero registration code. Dapper, Newtonsoft.Json,
MongoDB, and Swashbuckle do not, which is the new friction this phase has to address.

The generator also emits one small companion per package — a static `Register` method
that wires every generated type from the current assembly into the relevant
library-specific registry:

| Library | Registrar (emitted, opt-in to call) |
|---|---|
| Dapper | `OrionKey.Dapper.OrionKeyDapper.Register()` — calls `SqlMapper.AddTypeHandler` for every generated handler in the calling assembly |
| Newtonsoft.Json | `OrionKey.NewtonsoftJson.OrionKeyJsonSettings.Apply(JsonSerializerSettings)` — adds every generated converter to a settings instance |
| MongoDB | `OrionKey.Mongo.OrionKeyBson.Register()` — calls `BsonSerializer.RegisterSerializer` for every generated serializer |
| Swashbuckle | `services.AddOrionKeyOpenApi()` extension or `c.AddOrionKeyFilters()` for `SwaggerGenOptions` — registers every generated schema filter |

The registrars are emitted into the consumer's assembly (not a separate NuGet package)
and discover the generated types via the source generator. No reflection is used at
runtime — the generator knows every `[OrionId]` struct in the compilation and emits a
static list of registrations directly.

## Data flow

Compile time: `OrionIdGenerator.Handle` already receives the parsed `OrionIdModel` and a
flag for whether EF Core is referenced. We extend the `Initialize` method to compute a
small `IntegrationFlags` record (`HasEfCore`, `HasDapper`, `HasNewtonsoft`, `HasMongo`,
`HasSwashbuckle`) once per compilation, combine it with the per-symbol output, and pass
it into `Handle`. Each new emitter runs only when its flag is true; the
`RegistrationEmitter` runs once per assembly to wire everything found.

Runtime: each generated companion is a stand-alone type implementing the target
library's converter contract. Users either let the registrar wire them in one line at
startup, or register individual handlers by hand — both are supported.

## Error handling

- A `[OrionId<TValue>]` whose `TValue` is not supported by a target library
  (theoretically possible if we ever add `Guid` IDs and Mongo's `Guid` representation
  is misconfigured) reports a new diagnostic `ORIONKEY009 — integration-incompatible
  value type`. The current strategy/value-type matrix only allows `Guid`/`long`/`string`,
  all of which are natively supported by all four libraries, so this diagnostic is a
  safety net rather than an expected failure mode.
- The generator never throws if a target package's API surface differs from what the
  emitter expects; instead it reports `ORIONKEY010 — integration emitter skipped` and
  proceeds. This protects users on prerelease versions of the integration libraries.

## Testing

- **Emitter unit tests** — one file per new emitter under
  `tests/Moongazing.OrionKey.Generators.Tests/`. Each runs the generator with a tiny
  source plus the relevant library reference and asserts the generated code contains
  the expected `class`/`method`/`override` shapes. Patterned on
  `JsonConverterTests.cs` and `EfCoreConverterTests.cs`.
- **Conditional-emission tests** — assert each emitter produces *nothing* when its
  anchor type is absent from the compilation. The harness already controls the
  reference set via the existing `GeneratorHarness.Run` helper.
- **Integration round-trips** under `tests/Moongazing.OrionKey.IntegrationTests/`:
  - `DapperRoundTripTests` — SQLite in-memory, insert/query an entity keyed by an
    OrionKey ID through raw Dapper.
  - `NewtonsoftJsonRoundTripTests` — serialize/deserialize with `JsonConvert`.
  - `MongoRoundTripTests` — in-memory or testcontainer Mongo; if the latter pushes the
    test surface too high we fall back to a `Mock<IMongoCollection<T>>` exercising the
    serializer in isolation.
  - `OpenApiSchemaTests` — boot a minimal `WebApplication` with Swashbuckle, generate
    the document, assert the ID schema is `type: string` (or matching primitive).
- **Registration tests** — assert the emitted `Register()` companion enumerates every
  generated handler from the test assembly (compile-time discovery, runtime no-op).

Single release `0.3.0`. No breaking changes are intended; the new emitters are purely
additive. Users who do not reference Dapper / Newtonsoft / Mongo / Swashbuckle see no
behaviour difference. Phases C and D follow as separate specs and releases.
