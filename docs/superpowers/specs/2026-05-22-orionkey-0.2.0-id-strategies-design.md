# OrionKey 0.2.0 — New ID Strategies (Phase A)

**Date:** 2026-05-22
**Status:** Approved
**Release:** 0.2.0 (first slice of a phased 0.2.x → 0.5.x roadmap)

## Context

OrionKey 0.1.0 ships five generation strategies (`Snowflake`, `Ulid`, `NanoId`,
`GuidV7`, plus externally-assigned `int`/`long`). The next version expands the
library along four axes: new ID strategies, new integration emitters, AOT/trimming
compliance, and analyzer/code-fix improvements.

That total scope is too large for a single implementation plan, so the work is
decomposed into four independent phases, each shipping as its own minor release
with its own spec → plan → implementation cycle:

| Phase | Release | Content |
|---|---|---|
| **A** | **0.2.0** | **New ID strategies (this spec)** |
| B | 0.3.0 | Integration emitters: Dapper, Newtonsoft.Json, MongoDB, OpenAPI |
| C | 0.4.0 | Native AOT & trimming compliance |
| D | 0.5.0 | Analyzer/code-fix improvements + remaining stabilization |

This document specifies **Phase A only**.

## Goals

1. Add four new generation strategies: `Cuid2`, `Ksuid`, `ObjectId`, `SequentialGuid`.
2. Fix two latent ordering bugs in generated `CompareTo` (S1, S2 below) — folded in
   because Phase A adds sortable types that touch the same code.
3. Ship as `0.2.0` with full tests, benchmarks, and documentation.

## Non-goals

- Integration emitters, AOT work, analyzer improvements — deferred to Phases B/C/D.
- No new `ValueType`: `ObjectId` is stored as a 24-character hex `string`, so the
  existing `Guid`/`int`/`long`/`string` value types are sufficient.
- No change to the `[OrionId<TValue, TStrategy>]` public API shape.

## New strategies

| Marker | Storage (`TValue`) | `New()` output | Sortable | Notes |
|---|---|---|---|---|
| `Cuid2` | `string` | 24-char, lowercase letter-prefixed base36 | no | Collision-resistant, horizontally scalable |
| `Ksuid` | `string` | 27-char base62 (4-byte timestamp + 16-byte random) | yes | K-Sortable Unique ID, epoch 2014-05-13 |
| `ObjectId` | `string` | 24-char hex (4-byte timestamp + 5-byte random + 3-byte counter) | yes | MongoDB ObjectId layout, canonical hex representation |
| `SequentialGuid` | `Guid` | SQL Server-ordered sequential GUID (`NEWSEQUENTIALID`-style) | yes | Index-friendly clustered-key GUID |

Usage is identical to existing strategies:

```csharp
[OrionId<string, Cuid2>]        public readonly partial struct AccountId;
[OrionId<string, Ksuid>]        public readonly partial struct EventId;
[OrionId<string, ObjectId>]     public readonly partial struct DocumentId;
[OrionId<Guid, SequentialGuid>] public readonly partial struct InvoiceId;
```

### Strategy generation details

- **Cuid2** — first character is a random lowercase letter; remaining 23 are base36
  (`0-9a-z`) derived from a cryptographically-random source mixed with a per-process
  counter and entropy. Length fixed at 24. Not time-sortable.
- **Ksuid** — 20 payload bytes: a 4-byte big-endian seconds-since-epoch timestamp
  (epoch = 2014-05-13 00:00:00 UTC) followed by 16 cryptographically-random bytes;
  base62-encoded to a fixed 27 characters, left-padded.
- **ObjectId** — 12 payload bytes following the MongoDB layout: 4-byte big-endian
  Unix-seconds timestamp, 5-byte per-process random value, 3-byte big-endian counter
  initialised randomly and incremented per call; rendered as 24 lowercase hex chars.
- **SequentialGuid** — a GUID whose byte layout makes it ascending under SQL Server's
  `uniqueidentifier` sort order: the increasing component occupies the bytes SQL
  Server sorts last, so clustered-index inserts stay append-mostly.

## Stabilization fixes (folded into 0.2.0)

A review of `ComparableEmitter` surfaced two real ordering bugs. Both are fixed in
0.2.0. Because OrionKey is pre-1.0, these are treated as bug fixes, not breaking
changes, and are called out explicitly in the changelog.

- **S1 — Guid `CompareTo` does not preserve order.** `ComparableEmitter` emits
  `Comparer<Guid>.Default.Compare(...)` for Guid-backed sortable types. .NET's
  `Guid` comparison is field-by-field in a non-byte order, so a `GuidV7` ID marked
  *sortable* does **not** actually compare in timestamp order. `SequentialGuid`
  would inherit the same defect. **Fix:** for Guid-backed sortable strategies,
  emit a byte-order comparison (compare `ToByteArray(bigEndian: true)` spans, or an
  equivalent ordinal byte comparison) so `CompareTo` matches creation/index order.
- **S2 — String `CompareTo` is culture-sensitive.** `Comparer<string>.Default` is
  culture-sensitive; sortable string IDs (`Ulid`, and the new `Ksuid`/`ObjectId`)
  require ordinal comparison for stable, locale-independent ordering. **Fix:** for
  string-backed sortable strategies, emit `StringComparer.Ordinal`-based comparison.

`CompareTo` for non-sortable types is unaffected (no `IComparable` is emitted).

## Data flow

Unchanged from existing strategies:

1. User declares `[OrionId<string, Ksuid>] readonly partial struct EventId`.
2. `OrionIdParser` maps the attribute to an `OrionIdModel` (`ValueType.String`,
   `StrategyType.Ksuid`, `IsSortable = true`).
3. `OrionIdGenerator` runs the emitters; `CoreBodyEmitter` emits
   `New() => new(global::Moongazing.OrionKey.OrionKey.NewKsuid())`, `ComparableEmitter`
   emits an ordinal-string `CompareTo`.
4. At runtime `OrionKey.NewKsuid()` delegates to `KsuidFactory` (or, inside a
   `DeterministicIdScope`, to the sequential generator).

## Error handling

- An unsupported `TValue`/`TStrategy` pairing (e.g. `[OrionId<Guid, Cuid2>]`) is
  rejected by `IsCompatible`, raising the existing `ORIONKEY` incompatible-strategy
  diagnostic. New strategies extend `IsCompatible` so only the documented pairings
  compile.
- Factories use `RandomNumberGenerator` for entropy; no new exception types. The
  `ObjectId` per-process counter wraps modulo 2^24, matching the MongoDB spec.

## Testing

- **Factory unit tests** (`Moongazing.OrionKey.Tests`) — one file per factory:
  output length/charset/format, uniqueness across a large batch, and monotonic
  ordering for the sortable factories (`Ksuid`, `ObjectId`, `SequentialGuid`).
- **Generator tests** (`Moongazing.OrionKey.Generators.Tests`) — each new strategy
  emits the correct `New()` and the correct (or absent) `IComparable`.
- **Regression tests for S1/S2** — `GuidV7`/`SequentialGuid` IDs created in
  timestamp order compare ascending; sortable string IDs compare ordinally
  regardless of `CultureInfo.CurrentCulture`.
- **Integration tests** (`Moongazing.OrionKey.IntegrationTests`) — JSON, EF Core,
  and minimal-API round-trips for one ID of each new strategy.
- **Testing-package tests** (`Moongazing.OrionKey.Testing.Tests`) — deterministic
  scope produces repeatable values for the four new strategies.
